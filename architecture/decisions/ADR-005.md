# ADR-005: Minimal Role-Scoped Tools and `gh` CLI with Per-Job `GITHUB_TOKEN` Least Privilege

- **Decision ID:** D5 (Tools)
- **Date:** 2026-11-23

## Status

Accepted

## Context

Each agent needs a small, well-defined set of tools to read code, edit files, run repository build/test commands, and interact with GitHub. Providing overly broad tools (such as unrestricted shell access or a full GitHub MCP server with write endpoints) increases both token consumption (large tool-schema definitions on every turn) and security risk.

Per [GitHub Actions secure-use documentation](https://docs.github.com/en/actions/reference/security/secure-use) and [`GITHUB_TOKEN` permissions](https://docs.github.com/en/actions/concepts/security/github_token), each job receives an ephemeral token scoped strictly to its declared `permissions:` block.

### Options Considered

- **Option A — GitHub MCP Server (`github/github-mcp-server`) in Every Job:** Run the [GitHub MCP Server](https://github.com/github/github-mcp-server) Docker container for all agents. Rejected because: (1) container startup adds overhead to every job, (2) large MCP tool schemas inflate input tokens on every LLM turn, and (3) as documented in [GitHub Agentic Workflows guidance](https://github.github.com/gh-aw/reference/github-tools/), direct `gh` CLI usage is faster and cleaner inside Actions runners.
- **Option B — Unrestricted Bash + Full Workflow Permissions:** Give all agents bash and workflow-level `contents: write` + `pull-requests: write`. Rejected because it violates least privilege and allows Stage 1 or Stage 6 to mutate code or push commits.
- **Option C — Minimal Python Tool Wrappers + Deterministic `gh` CLI Steps + Per-Job `GITHUB_TOKEN` Permissions (Chosen):** Give each agent only the minimal Python tool functions required for its role, keep all GitHub mutations in deterministic `gh` CLI wrappers, and enforce permissions at the Actions job level.

## Decision

We enforce **two-layer least privilege**: (1) workflow-level `permissions: {}` (deny all by default) with minimal per-job `permissions:`, and (2) strict per-agent tool allowlists in the Python harness (`workflow/tools.py`).

### Per-Job Permission & Tool Matrix

| Actions Job | Component | `GITHUB_TOKEN` `permissions:` | Allowed Agent Tools | Explicitly Forbidden |
| :--- | :--- | :--- | :--- | :--- |
| `plan` | Agent 1: Planner (Stages 1–2) | `contents: read`, `issues: write` | `read_file`, `list_files`, `search_code`, `write_artifact` (artifacts dir only) | Editing repo files, shell execution, `git push`, PR APIs |
| `build-r1` / `rework-r2` | Agent 2: Builder (Stages 3–4) | `contents: read` | `read_file`, `edit_file` (scoped to repo config allowlist), `run_build`, `run_tests`, `git_diff`, `write_artifact` | `git push`, `gh` write commands, editing `.github/` or `workflow/` (outbound network is *not* blocked; see ADR-009) |
| `release-r1` / `release-r2` | Deterministic Script (Stage 5) | `contents: write`, `pull-requests: write`, `issues: write` | No LLM. Deterministic script runs `git push`, `gh pr create`/`edit`, renders `pr.md` | `gh pr merge`, pushing to default branch (`main`/`master`), modifying code |
| `ci-r1` / `ci-r2` | Deterministic CI (Stage 5 check) | `contents: read`, `statuses: write` | No LLM. Runs `ci_cmds` from `.autose.yml` at the PR head SHA and posts the `autose/ci` commit status | Any write to code, PRs or issues |
| `review-r1` / `review-r2` | Agent 3: Independent Reviewer (Stage 6) | `contents: read`, `pull-requests: write` | `read_file`, `search_code`, `git_diff`, `run_tests` (ephemeral local worktree), `write_artifact(review.md)`; the job posts the review with `gh pr review --comment` | `git push`, editing repo files, `gh pr merge`, downloading Stage 1–5 artifacts |

Repository-specific build and test commands are read from a small repo config file (`.autose.yml`, e.g., `build_cmd`, `test_cmd`, `ci_cmds`, `allowed_edit_paths`, `base_branch`), keeping all tool wrappers 100% repository-agnostic.

**Repository settings this design depends on.** `GITHUB_TOKEN` can open pull requests only when the repository setting *Allow GitHub Actions to create and approve pull requests* is enabled. Because the PR author is then `github-actions[bot]`, the reviewer job, using the same token, cannot submit an `APPROVE` review (GitHub rejects approving your own pull request). The reviewer therefore always posts a `COMMENT` review whose first line states the verdict, and the machine-readable verdict lives in `review.md` (ADR-008).

## Consequences

### Positive

- **Enforced at the Platform Level:** Even if an agent attempts `git push` during Build or Review, GitHub's API rejects it because those jobs only hold `contents: read`.
- **Lower Token Overhead:** Each agent sees only 4–6 small, focused tool schemas instead of dozens of unused GitHub MCP endpoints.
- **Zero Accidental Merges:** No tool wrapper or script invokes `gh pr merge`; branch protection enforces human merge authority.

### Negative

- **Requires `.autose.yml` Per Repository:** Onboarding a new repository requires defining a short ~10-line `.autose.yml` (build command, test command, allowed paths, base branch), which is a small one-time setup cost for full repo portability.
- **No Native Approval:** The bot's verdict is a `COMMENT` review, not a GitHub approval, so branch-protection rules that count approvals only ever see a human's approval. We accept this, since the final merge decision belongs to a person anyway.
- **GitHub CLI Coupling:** Stage 5 and Stage 6 publishing rely on `gh` CLI (pre-installed on GitHub-hosted runners), which is appropriate for a GitHub Actions workflow.
