# ADR-012: Let the planner fix a rejected spec or design once

- **Decision ID:** D7 (Checks), revisited
- **Date:** 2026-11-23
- **Supersedes:** the "halt on the first failed check" rule for Stages 1 and 2 in ADR-007

## Status

Accepted

## Context

ADR-007 says a stage whose check fails explains why in its artifact and stops the run. For
Stages 3 and 4 the builder already gets its failures back and can try again (ADR-002), but for
Stages 1 and 2 the planner got no second chance. A format-only repair was allowed, nothing else.

The second run on issue #3 ([run 45172879048](https://github.com/Anjaliy474/tinydb/actions/runs/45172879048))
showed the cost of that. The planner wrote a reasonable spec, but one of its three acceptance
criteria said an existing test "continues to function correctly". The testability judge rightly
called that untestable, and the whole run stopped after one minute. The fix needed was one
sentence, and the checker had already said exactly what was wrong.

### Options considered

- **A: keep halting.** Strict and simple, but a run dies on problems the planner could fix from
  the checker's message, and a person has to restart it by hand.
- **B: let the planner retry until the check passes.** Fixes more specs, but it's an open loop
  and costs free-tier calls with no clear end.
- **C: one revision with the checker's reasons, then halt (chosen).** The planner sees the exact
  reasons and rewrites the artifact once in the same conversation. The gate checks the new
  version and still makes the final decision.

## Decision

- After a failed Stage 1 or Stage 2 check, the planner gets one revision (`plan_revisions: 1`
  in `.autose.yml`) with the gate's reasons, then the gate runs again. If it still fails, the
  stage stops and explains why, as in ADR-007.
- A spec the planner itself marks `status: blocked` is not revised; that means the issue needs a
  person.
- The plain-code check now also rejects "correctly", "as expected", "as before", "works" and
  "normally" in acceptance criteria, so this kind of wording is caught before the model judge,
  and the spec prompt asks for an exact result in criteria that protect existing behaviour.

## Consequences

### Positive

- One unclear sentence no longer kills a run. The bound is fixed (one revision), so runs still
  end in a known number of steps.
- Stages 1-2 and Stages 3-4 now follow the same idea: plain code finds the problem, the agent
  gets to fix it within a fixed budget, plain code decides.

### Negative

- A revised spec might satisfy the checker on wording without being a better spec. The
  reviewer, who reads the original issue rather than the spec, is still there to catch that.
- A revision costs a few more model calls on the free tier.
- The longer vague-word list could reject a criterion that uses "works" in a precise way. If
  that happens, the revision gives the planner a chance to rephrase.
