# ADR-002: Finite Deterministic State-Machine Control Flow Across Multi-Job GitHub Actions

- **Decision ID:** D2 (Control Flow)
- **Date:** 2026-11-23

## Status

Accepted

## Context

The workflow must enforce six fixed stages with mandatory pass/fail gates and bounded backward transitions:
- Stage 4 (Testing) returns to Stage 3 (Implementation) when tests fail, and escalates/halts if repeated failures indicate a flawed design.
- Stage 6 (Review) returns requested changes to Stage 3 (`code_issue`) or Stage 2 (`approach_issue`), capped at **at most two review rounds**.
- Any stage whose check fails must explain why in its artifact and terminate the run.
- Tests that keep failing can mean the design is wrong, not only the code, so the workflow needs a bounded way back to Stage 2 from Stage 4.
- Pushes and pull requests made with `GITHUB_TOKEN` do **not** trigger other workflows ([GitHub docs](https://docs.github.com/en/actions/concepts/security/github_token)), so the repository's own CI (`ci-workflow.yml`) will not run on the bot's PR. The Stage 5 check ("CI passes") must therefore be produced inside this workflow.

To keep token usage predictable and prevent runaway execution, control flow must be **finite and deterministic**—never an open-ended LLM loop where a model decides indefinitely what to do next. At the same time, [GitHub Actions jobs](https://docs.github.com/actions/using-workflows/workflow-syntax-for-github-actions) form a directed acyclic graph (`needs:`), and job-level isolation is required to enforce separate permissions for Release and Review.

### Options Considered

- **Option A — Autonomous LLM Orchestrator / Planner Loop:** A manager agent dynamically chooses the next stage and decides when to stop. Rejected because it is non-deterministic, burns extra orchestration tokens on every step, and risks infinite loops or skipped gates.
- **Option B — Separate Event-Chained Workflows (`workflow_run` / self-comments):** Split stages into multiple `.yml` files triggering each other. Rejected because GitHub blocks `GITHUB_TOKEN` from triggering recursive workflows (requiring a PAT/GitHub App) and fragments one logical run across multiple Actions logs.
- **Option C — Finite Deterministic State Machine (FSM) Embedded in an Unrolled Multi-Job Actions DAG (Chosen):** Deterministic Python controls bounded internal retries, and GitHub Actions YAML unrolls the hard 2-round review cap into explicit conditional jobs.

## Decision

We implement a **strictly finite, deterministic state machine** in `.github/workflows/autose.yml` backed by a deterministic Python controller (`workflow/orchestrator.py`):

1. **Job 1 — `plan` (Agent 1: Stages 1–2):** Runs Stage 1 (`spec.md` + Gate 1), then Stage 2 (`design.md` + Gate 2). Exits non-zero and stops the workflow if either gate fails.
2. **Job 2 — `build-r1` (Agent 2: Stages 3–4, Round 1):** `workflow/orchestrator.py` runs Stage 3 (`diff.patch` + Gate 3) and Stage 4 (`test_report.md` + Gate 4) inside a finite loop capped at **max 3 attempts**.
   - If Gate 4 fails, control deterministically loops back to Stage 3 with the failing test output.
   - If all 3 attempts fail, or the same failure signature repeats twice in a row, the FSM treats this as evidence that the design, not just the code, is wrong and **escalates once to Stage 2**: Agent 1 is re-invoked in-process with a fresh context and its read-only tools, given `spec.md`, the current `design.md` and a short failing-test summary, and must produce a revised `design.md` that passes Gate 2. Agent 2 then gets one more cycle of at most 3 attempts against the revised design.
   - If that second cycle also fails, the FSM stops, records the diagnostic reason in `test_report.md`, and halts the run. At most one design escalation happens per round.
3. **Job 3 — `release-r1` (Deterministic Script: Stage 5, Round 1):** Pushes branch `autose/issue-<N>`, opens or updates the PR, and writes `pr.md`.
4. **Job 4 — `ci-r1` (Deterministic CI: Stage 5 check, Round 1):** Checks out the PR head SHA in a fresh job (`contents: read`, `statuses: write`), runs the CI commands from `.autose.yml` (`ci_cmds`: test suite and type check), and posts the result as an `autose/ci` commit status so it appears on the PR. Gate 5 passes only if the PR is open and `ci-r1` succeeded.
5. **Job 5 — `review-r1` (Agent 3: Stage 6, Round 1):** Isolated job (`contents: read`). Produces `review.md` and outputs `verdict` (`APPROVE` | `REQUEST_CHANGES`) and `routing_target` (`implementation` | `design` | `none`).
6. **Conditional Round 2 Jobs (`rework-r2` → `release-r2` → `ci-r2` → `review-r2`):**
   - Execute **only if** `needs.review-r1.outputs.verdict == 'REQUEST_CHANGES'`.
   - If `routing_target == 'design'`, `rework-r2` runs Agent 1 (Stage 2 only, updating `design.md` + Gate 2) followed by Agent 2 (Stages 3–4, max 3 attempts).
   - If `routing_target == 'implementation'`, `rework-r2` runs Agent 2 (Stages 3–4, max 3 attempts) directly.
   - `release-r2` pushes updated commits to the same PR branch, and `ci-r2` re-runs CI on the new head (`Gate 5`).
   - `review-r2` runs the second and final independent review. Whether `review-r2` approves or requests further changes, the workflow terminates cleanly and hands the PR to a human maintainer.

### Transition Decision Authority

| Transition | Decided By | Hard Bound |
| :--- | :--- | :--- |
| Stage 1 → 2 → 3 → 4 → 5 → 6 | Deterministic gate exit code (`workflow/gates.py`) | Halt immediately on failure |
| Stage 4 → Stage 3 | Deterministic test-runner failure (`Gate 4`) | Max 3 attempts per cycle; early exit on repeated identical error |
| Stage 4 → Stage 2 | Orchestrator, after a cycle of Stage 3 attempts is used up | Max 1 design escalation per round; halt if the next cycle also fails |
| Stage 6 → Stage 2 or Stage 3 | Agent 3 structured verdict JSON, enforced by Actions `if:` | Max 1 rework cycle (2 total review rounds); hard stop after `review-r2` |

## Consequences

### Positive

- **Guaranteed Termination & Bounded Tokens:** Every loop has a code- or YAML-level upper bound (per round: at most 2 Builder cycles of 3 attempts and 1 design escalation; at most 2 review rounds). Infinite execution is structurally impossible.
- **Zero Orchestration Token Overhead:** Deterministic Python and YAML `if:` expressions make all routing decisions at zero LLM cost.
- **Single Traceable Run:** The entire lifecycle from issue trigger through Round 2 review appears inside one GitHub Actions workflow graph.

### Negative

- **YAML Repetition for Round 2:** Unrolling Round 1 and Round 2 duplicates job wiring in `.github/workflows/autose.yml`, mitigated by calling the same reusable Python entrypoint (`workflow/run_stage.py`) with a `--round` flag.
- **Fixed Round Limit:** Supporting more than 2 review rounds requires editing YAML (acceptable since the 2-round ceiling is an explicit architectural invariant).
- **Reduced In-Run CI:** `ci-r1` runs one OS and one Python version from `.autose.yml`, not the upstream 17-job matrix in `ci-workflow.yml`. It is faster and cheaper but can miss platform-specific failures; the full upstream CI still runs whenever a person pushes to the branch.
