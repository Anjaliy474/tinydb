# ADR-001: Three-Agent Role-Specialized Decomposition with Deterministic Release

- **Decision ID:** D1 (Splitting the Work)
- **Date:** 2026-11-23

## Status

Accepted

## Context

The AutoSE workflow must execute six fixed SDLC stages—(1) Requirements, (2) Design, (3) Implementation, (4) Testing, (5) Release, and (6) Review—against **any** target repository configured with a build command and a test suite.

When deciding how many LLM agents to run, three constraints dominate:
1. **Token Efficiency:** Every additional agent boundary introduces cold-start prompt overhead and repeated repository exploration. A six-agent pipeline burns tokens re-reading the same files across tightly coupled stages.
2. **Deterministic Boundaries & Least Privilege:** Untrusted issue parsing (Stage 1), code execution (Stages 3–4), GitHub publishing (Stage 5), and independent auditing (Stage 6) require distinct permission levels. A single monolithic agent mixes untrusted input with write/push permissions and cannot independently review its own code.
3. **Clean Re-entry on Review Feedback:** Stage 6 must be able to route requested changes back either to Stage 2 (approach/design issue) or Stage 3 (code/test issue).

### Options Considered

- **Option A — 1 Monolithic Agent (Stages 1–5) + 1 Reviewer (2 agents total):** Minimizes hand-offs, but mixes untrusted issue text with code-editing tools, bloats context across planning and debugging, and forces re-running Requirements/Design even for minor code-level review fixes.
- **Option B — 1 Agent Per Stage (6 agents total):** Maximizes modularity, but duplicates repository reading tokens between Requirements→Design and Implementation→Testing, and wastes LLM calls on Stage 5 (Release), which is mechanical Git/PR automation.
- **Option C — 3 Specialized LLM Agents + Deterministic Stage 5 Automation (Chosen):** Group tightly coupled read-only planning (Stages 1–2) and write/test execution (Stages 3–4), remove the LLM from Stage 5 entirely, and isolate Stage 6 as an independent reviewer.

## Decision

We divide the six SDLC stages across **three LLM agents** plus **one deterministic non-LLM release step**:

| Component | Stages Handled | Role & Scope | Output Artifacts |
| :--- | :--- | :--- | :--- |
| **Agent 1: Planner** | Stage 1 (Requirements), Stage 2 (Design) | Read-only. Uses the A1 specification skill to turn the issue into testable acceptance criteria (`spec.md`), passes Gate 1, then uses `ARCHITECTURE.md` and the repo tree to list exact files and functions to change (`design.md`). | `spec.md`, `design.md` |
| **Agent 2: Builder** | Stage 3 (Implementation), Stage 4 (Testing) | Local read/write (no `git push`). Implements the plan in `design.md` on a feature branch (`diff.patch`), passes Gate 3 (build), then writes one test per acceptance criterion and runs the full test suite (`test_report.md`), retrying Stage 3 within a finite budget if tests fail. | `diff.patch`, `test_report.md` |
| **Deterministic Release Script (No LLM)** | Stage 5 (Release) | Pure shell/CLI automation. Pushes the feature branch, opens or updates the PR via `gh`, renders `pr.md` from a deterministic template populated with verified artifacts, CI then runs in a separate job in the same run (`ci-r1`, ADR-002), because PRs opened with `GITHUB_TOKEN` do not trigger the repository's own CI workflow. | `pr.md` + PR link |
| **Agent 3: Independent Reviewer** | Stage 6 (Review) | Isolated Actions job, fresh context, read-only repo (`contents: read`), no push permission. Inspects only the issue, the PR diff, and the repo at PR HEAD, optionally runs tests, and outputs a verdict (`APPROVE` or `REQUEST_CHANGES` routed to Stage 2 or Stage 3). | `review.md` |

Within Agent 1 and Agent 2, each stage remains separated by its mandatory deterministic gate (ADR-007). Stage 2 never runs if Stage 1 fails its check; Stage 4 never runs if Stage 3 fails to build.

## Consequences

### Positive

- **Lower Token Consumption:** Only three LLM agents run per cycle. Keeping Stages 1–2 together avoids re-explaining requirements; keeping Stages 3–4 together lets the Builder fix failing tests using its warm context of edited files; making Stage 5 deterministic uses zero LLM tokens.
- **Clear Privilege Separation:** Agent 1 is strictly read-only, Agent 2 cannot push to GitHub, the deterministic Stage 5 script holds the only `contents: write` token, and Agent 3 cannot modify code or push.
- **Direct Review Routing:** `approach_issue` feedback routes cleanly to Agent 1 (Stage 2); `code_issue` feedback routes cleanly to Agent 2 (Stage 3).

### Negative

- **Shared Builder Context Across Implementation and Testing:** Because Agent 2 writes both the implementation and the acceptance tests, it could write weak tests that mirror its own code assumptions. We mitigate this via two controls: (1) deterministic Gate 4 verifies 1-to-1 coverage of every `AC-i` in `spec.md`, and (2) Agent 3 (Independent Reviewer) audits test adequacy from a fresh context and can run its own edge-case probes (ADR-008).
- **Rigid `pr.md` Formatting:** A deterministic Stage 5 template produces uniform, structured PR descriptions rather than custom prose—which is preferable for auditability and token savings.
