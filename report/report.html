From issue to pull request: an agentic SDLC workflow

AutoSE Assignment 3 · Roll no. 2025204015 · Repository: github.com/Anjaliy474/tinydb (fork of TinyDB pinned at edff96a, tag autose-base)

For this assignment I built a GitHub Actions workflow on a fork of TinyDB. A maintainer puts the label autose on an issue, or comments /autose, and the workflow writes a spec, plans the change, edits the code, tests it, opens a pull request and gets it reviewed by a separate agent. It never merges anything. That decision stays with a person.

The agents ran on two model providers. I started on Google's Gemini free tier and later moved to DeepSeek's paid API, because the free tier kept running out of quota. Section 2 explains why, and the runs from both are in the results.

1. Architecture

I split the work between three agents and a few plain scripts. The Planner does Stages 1 and 2, the Builder does Stages 3 and 4, a release script does Stage 5 and an independent Reviewer does Stage 6. Before all of that, an intake step checks whether the person who triggered the run is allowed to, and at the end a finalize step records how many review rounds were used. Every stage is its own Actions job, and each job only gets the GitHub permissions it needs. Whether a stage passed is decided by ordinary code in gates.py, never by the agent that did the work.

A run can't go on forever. In each round the Builder gets at most two cycles of three attempts, with one design revision in between, and there are at most two review rounds. Every stage also has a turn limit, a token limit, a cost limit and a job timeout. Each job checks out the workflow code from master into its own folder, separate from the code being changed, so a pull request can't change the rules it is checked against.

Models. The first five runs used the Gemini free tier: gemini-3.5-flash-lite for planning, gemini-3.5-flash and gemini-3.6-flash for building and reviewing, and other Gemini models as fallbacks when one ran out of quota (the one build that finished ended up on Flash-Lite). Every run after that used DeepSeek: deepseek-flash (DeepSeek V4.1 Flash) for the planner and builder, and at first deepseek-v4-pro (V4 Pro) for the reviewer. In the end I put every role on deepseek-flash to keep it simple and cheap, and used V4 Pro again only in experiment A.

The three decisions that mattered most

Plain code decides, not the agents (ADR-007, changed by ADR-012). A stage only hands over when gates.py says so. The design check parses the plan and makes sure every function it names really exists. The test check runs the whole suite and makes sure each acceptance criterion points to a new test that passed. These checks caught real mistakes: a criterion that said an existing test "continues to function correctly" was rejected as untestable, and a builder that pointed a criterion at a test that didn't exist was sent back. They also showed my own bugs first, for example a parser that only read the first line of a criterion written over two lines. So I kept the gates small and covered them with tests (38 in the end). The one thing I changed was stopping on the first failure. Run 45172879048 died after a minute because of one vague sentence that the checker had already explained, so now the planner gets exactly one chance to fix the file using the checker's reasons. In the run in Figure 2, that second try is what got Stage 1 through.

Keeping the reviewer independent (ADR-008, ADR-003). I didn't want independence to depend on the prompt asking nicely, so it's built into the structure. The reviewer runs in its own job with a read-only checkout of the PR and never downloads the spec, the design or any of the other agents' notes. It gets what a human reviewer would get: the issue, the diff and the code, and it can run the tests and its own small Python probes. An approval has to be backed by evidence. The gate rejects a review that didn't run the tests or skipped one of the four checks, and every blocking problem needs a file and a line. GitHub doesn't let a bot approve its own PR anyway, so the reviewer posts a comment with its verdict, and only a person can approve and merge. Because it reads the issue and not the spec, it judges what the user asked for, not the planner's version of it.

The model choice, which I had to make three times (ADR-006, 011, 013). I designed for Claude and then found out I had no paid API access. I moved to the Gemini free tier and added what it needed: waiting for the delay the server asks for, stopping straight away when the daily quota is gone, and a list of fallback models for each role. Each of the five Gemini runs on issue #3 showed me something to fix, but four of them failed on overload or quota, and the one that finished spent about 45 minutes in the builder. When I moved to DeepSeek, the same pipeline ran an issue from start to end in about six minutes for nine cents. The structure stayed the same across all three providers. Only the model code and the limits changed: DeepSeek needed 40 builder turns instead of 20, because it takes one small step at a time.

3. Decision experiments

I tested two decisions on five seeded PRs (experiment/seeded_prs/). Four contain a bug I planted and one is a correct fix. All five pass TinyDB's own test suite, so the reviewer can't find the bugs just by running the tests. I kept the answer key outside the repository until every review was finished. All reviews here ran on DeepSeek.

What happened. Neither change moved a single verdict. Every setup caught all four bugs and approved the clean PR, and each time it named the file and line, usually with a probe that showed the bug happening. For both ADRs as I wrote them, that's a negative result. On these seeds, the structure (own job, no upstream files, a review that needs evidence) seems to do most of the work. Two differences were real, though. With the skeptical prompt the reviewer checked much harder before approving: 7 probes on the clean PR instead of 3, which is what ADR-008 was after. And only V4 Pro saw that S1's approach was wrong rather than its code, and sent it back to the design stage. In a second round that decides whether the change gets re-planned or just patched. It also cost 3.3 times as much.

What I changed. I kept Flash with the skeptical prompt as the default reviewer. The experiment also found two bugs in my harness. The model= option didn't accept DeepSeek names, and a review sent back in the wrong JSON shape crashed the job. ADR-007 already allowed one repair pass for format problems, so now the reviewer gets one chance to send it again. If I kept going, I'd use V4 Pro only to double-check where a "request changes" verdict should be routed.

PR #16 for issue #3 was built on the Gemini free tier, but its Gemini reviewer had no quota left, so DeepSeek V4 Pro reviewed it later. The other four were built and reviewed on DeepSeek.

Pass rate per stage over all 14 full runs (results/results.csv), including the runs I used for debugging: planner 8/14, builder 5/8, release 5/5, CI 5/5, review 4/5. On Gemini, 0 of 5 runs finished. They failed on overload and quota, and the one review that failed was out of quota. On DeepSeek, 4 of 9 finished. The other five stopped on problems in my harness (turn limits set for Claude, a judge answer that got cut off, criteria written over several lines). I fixed each one and ran it again. Altogether the runs used about 5.9 million tokens and cost about $0.85 on DeepSeek. The Gemini runs were free.

What the reviewer caught. On the seeded PRs it found all four planted bugs, each with a probe, plus real problems I hadn't planted: in S3, limit=0 permanently caches an empty result, and S4's crash leaves the data half updated. It approved all five of the agents' own PRs but still pointed out things a person should look at. On #6 it noticed that a user document whose only key is the special date tag would quietly turn into a date when read back.

Where it got it wrong. The Flash reviewer sent S1 back to "implementation" when the approach was the problem. On #6, the date-tag problem is arguably a real bug that it let through as non-blocking. It also noticed that my seeded tests had "seeded" in their names, a hint I didn't mean to give.

5. Hindsight

The first decision I'd change is the model choice (ADR-006). I picked models for their ability and price, and only found out at the first run that I couldn't use them, and then that the Gemini free tier was too slow and too small for this. Next time I'd treat access, quotas and how each model behaves as part of the design. I'd check them with a one-call test before writing any agent code (the "check models" workflow I only added later), and I'd make the provider and all the limits plain settings from the start. Turn limits, timeouts and token caps all changed twice because I had set them for a model I never actually ran. I'd also give the planner its one revision from day one, instead of stopping the run. The builder already had retries, so the planner should have had them too.

6. Limitations and threats to validity

  • Small sample. Five issues and five seeded PRs, with one run per experiment cell. A 4/4 against 4/4 tie says little about the cases where the setups would differ, and a single different verdict would change the picture.
  • I made everything I measured with. The issues, hidden tests, seeds and prompts are all mine, so they may fit each other too well. The hidden tests for the vague issue accept more than one reasonable answer, which also makes it easier to pass.
  • The system changed while I measured it. The results come from a harness that kept changing (two providers in real runs, several fixes). The final setup, Flash for every role, reviewed only two of the five issue PRs. V4 Pro reviewed the other three.
  • Round 2 never ran for real. Every agent PR was approved in round 1, so the path back to the builder or planner is only covered by unit tests.
  • Same provider for builder and reviewer. In the final setup they are even the same model, so they may miss the same things. Only experiment A used a different model.
  • Safety gaps. GitHub's runners don't block network access, so code written by the builder can make outbound requests while the tests run. It has no secrets to send, though. The hidden tests are now in the repository, so any later run could read them.

AI use. I used Claude Code as a coding assistant for parts of the harness and documentation. I checked everything it produced, and the design decisions in the ADRs are mine. All runs, PRs and reviews in this report are real and linked in results/runs.md.
