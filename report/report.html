From issue to pull request: an agentic SDLC workflow

AutoSE Assignment 3 · Roll no. 2025204015 · Repository: github.com/Anjaliy474/tinydb (fork of TinyDB pinned at edff96a, tag autose-base)

A maintainer adds the label autose to an issue, or comments /autose. A GitHub Actions workflow then writes a spec, plans the change, edits the code, tests it, opens a pull request, runs CI and has the PR reviewed by a separate agent. The bot never merges; a person does. This report explains how the workflow is split up and why, what I tried and what changed when real runs proved me wrong.

1. Architecture

There are three agents and three plain scripts. The Planner does Stages 1 and 2, the Builder Stages 3 and 4, a release script Stage 5, and an independent Reviewer Stage 6. An intake step decides whether an event may start a run and a finalize step records how many review rounds are used. Each stage runs in its own Actions job with only the token permissions it needs. A plain-code module, gates.py, decides whether each stage passed; the agents never certify their own work.

The three decisions that mattered most

Plain code decides, not the agents (ADR-007, refined by ADR-012). Every stage hands over only after gates.py says so: the design gate parses the file and checks that every function it names exists; the test gate runs the full suite with a JUnit report and checks that each acceptance criterion maps to a new test that passed. This caught real problems: a spec criterion that said an existing test "continues to function correctly" was rejected as untestable, and a builder that mapped a criterion to a test that didn't exist was sent back. Gates also turned out to be the place where my own bugs showed up first (a parser that read only the first line of a wrapped criterion), which is a good argument for keeping them small and tested: the harness has 38 unit tests. The one thing I changed was the "halt on first failure" rule. Run 45172879048 stopped after one minute because of one vague sentence the checker had already explained, so ADR-012 gives the planner exactly one revision with the checker's reasons. In the sequence run above, that revision is what made Stage 1 pass.

Reviewer independence by structure, not by asking nicely (ADR-008, ADR-003). The reviewer runs in its own job with a read-only checkout of the PR head and never downloads the spec, the design or any transcript. It sees what a human reviewer sees: the issue, the diff and the code, and it can run tests and its own Python probes. Its approval has to be earned: the gate rejects a review that didn't run the tests or skipped one of the four audit dimensions, and a blocking defect needs a file and line. Because GitHub doesn't let a bot approve its own PR, it posts a COMMENT review with the verdict on the first line, and a person stays the only one who can approve and merge. Reading the issue instead of the spec matters: the reviewer judges what the user asked for, not the planner's interpretation of it.

Models: three versions of one decision (ADR-006 → 011 → 013). I designed for Claude, then found I had no paid API access. I moved to Gemini's free tier and built what that needed: retries that read the server's suggested delay, failing fast on a daily quota, a list of fallback models per role. Five runs on one issue each found a weakness and fixed it, but four failed on overload or quota and the one that worked took about 45 minutes in the builder. On DeepSeek the same pipeline ran an issue end to end in about six minutes for nine cents. The structure never changed across the three; only the backend and the limits did (DeepSeek needed 40 builder turns instead of 20 because it takes one small step per turn). The lesson is in the hindsight section.

3. Decision experiments

I tested two decisions on five seeded PRs (experiment/seeded_prs/). Four have a bug I planted and one is a correct fix; all five pass TinyDB's own suite, so the bugs can't be found by just running the tests. The answer key stayed outside the repo until every review was done.

What it showed. Neither decision changed a single verdict: every setup caught all four bugs and approved the clean PR, each time with a file, a line and usually a probe that reproduced the bug. That is a negative result for both ADRs as stated; on these seeds the structural controls (own job, no upstream artifacts, evidence-gated rubric) seem to do the work. Two differences were real. The skeptical prompt made the reviewer check much harder before approving (7 probes on the clean PR against 3), which is the behaviour ADR-008 asked for. And only the bigger model saw that S1's approach, not its code, was wrong, and routed it to the design stage; with round 2 that decides whether the change is re-planned or only patched. It cost 3.3 times as much.

What I changed. I kept the cheap Flash reviewer with the skeptical prompt as the default. The experiment also exposed two bugs in my harness: the reviewer's model= option didn't accept DeepSeek names, and a review whose JSON had the wrong shape crashed the job. ADR-007 already allowed one format-repair pass, so the reviewer now gets one chance to resubmit. The next design change I'd make is to confirm the routing of a REQUEST_CHANGES verdict with the Pro model only.

Pass rate per stage over all 14 full runs (results/results.csv): planner 8/14, builder 5/8, release 5/5, CI 5/5, review 4/5. These include the debugging runs. On the Gemini free tier 0 of 5 runs finished (overload, quota; the review that failed was out of quota); on DeepSeek 4 of 9 did. The five DeepSeek failures were limits and parsing problems in my harness (turn limits set for Claude, a cut-off judge answer, wrapped criteria), each fixed and re-run. All runs together used about 5.9 million tokens and cost about $0.85; the Gemini runs were free.

What the reviewer caught. On the seeded PRs: all four planted bugs, each with a probe, and extra real problems I hadn't planted, such as limit=0 permanently caching an empty result in S3 and the partial update left behind by S4's crash. On the agents' own PRs it approved all five, but still raised non-blocking points that are worth a person's attention; on #6 it found that a user document whose only key is the reserved date tag would be silently turned into a date.

Where it was wrong. The Flash reviewer routed S1 to "implementation" when the approach was wrong. On #6 the reserved-key problem is arguably a real defect that it let through as non-blocking. And it noticed my seeded tests had "seeded" in their names, a hint I didn't intend to give.

5. Hindsight

The decision I would change first is the model decision (ADR-006). I picked models by capability and price, and only found out at the first run that I had no access, then that the free tier was too slow and too small. I would now treat provider access, quotas and per-model behaviour as a design input, check them with a one-call probe before writing any code (the "check models" workflow I added late), and build the provider layer and the limits as configuration from day one. Turn limits, timeouts and token caps all had to change twice because I had tuned them for a model I never ran. Second, I'd let the planner revise once from the start (ADR-012) instead of halting: the builder already had retries, and the planner deserved the same.

6. Limitations and threats to validity

  • Small sample. Five issues and five seeded PRs, one run per experiment cell. A 4/4 tie says little about cases where the reviewer setups would differ; a single different verdict would change the picture.
  • I wrote everything I measured with. The issues, hidden tests, seeds and prompts are mine, so they may suit each other. The hidden tests accept several reasonable answers for the vague issue, which also makes it easier to pass.
  • The system changed during the experiment. Results come from an evolving harness (three providers, several fixes). The final configuration, Flash for every role, reviewed only two of the five issue PRs; the others were reviewed by Pro.
  • Round 2 was never exercised for real. Every agent PR was approved in round 1, so the rework path (reviewer → builder or planner) is tested only by unit tests, not by a real run.
  • Reviewer and builder share a provider and, in the final setup, the same model, so they may share blind spots. Only experiment A used a different model.
  • Safety limits. GitHub-hosted runners don't isolate the network, so code written by the builder can make outbound requests while tests run (it has no secrets to send). The hidden tests are now in the repository, so any later run could read them.
